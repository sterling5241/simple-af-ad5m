Found the decryption key/method
------------------------------------
Pulled /usr/prog/mytar (a tiny real binary, referenced by
app_startup.sh) out of the extracted factory tree (see
factory-reset.txt) and dumped its strings. It contains, in plaintext,
the exact command it runs via system():
  openssl des3 -d -k FFP0302~%@ffroot800 -salt -in %s | tar xvf - -C /usr/data/update/
Key: `FFP0302~%@ffroot800`, cipher DES3 (des-ede3-cbc), OpenSSL
`Salted__` format. Verified byte-exact via a raw hex dump around the
string in the binary (no truncation/extraction error).

Decrypted locally with modern OpenSSL 3.5.7:
  openssl enc -des3 -d -k 'FFP0302~%@ffroot800' -md md5 -salt -in <file> -out out.tar
IMPORTANT: modern OpenSSL's `enc` no longer defaults to MD5 for its
legacy key-derivation function the way OpenSSL 1.0.2d (what this
device actually bundles/was built against) did - `-md md5` must be
passed explicitly or it fails with "bad decrypt". This is the
complete, working, real recipe for decrypting any FlashForge AD5X/AD5M
update package obtained in the future.

The real OS-update flashforge_init.sh - the master orchestrator
------------------------------------------------------------------------
Read in full - ties every piece already documented in
../boot/ota-system.txt and ../boards/ together. Described below in the
order the functions are DEFINED in the script, which is NOT the real
execution order - the real call order at the bottom of the script is:
update_other, update_control, update_kernel, update_software,
update_library (create_key is commented out, never called). Notably,
update_other runs FIRST, before kernel/control, not last.

    but with a real, documented BYPASS: if a file named `screwflag`
    sits alongside this script, the machine-type check is skipped
    entirely ("screwflag" = a real factory/production marker, per its
    own Chinese comment: present "in the factory, can upgrade
    arbitrarily").

  - update_kernel(): finds the newest local `kernel-*.tar.xz`,
    extracts it to a temp dir under /usr/prog/PROGRAM/kernel/, verifies
    `md5sum.list`, moves it into place as .../kernel/<version>/, then
    runs that version's own run.sh - this IS exactly the real
    PROGRAM/kernel/2.0.1/run.sh already documented in
    ../boot/ota-system.txt, now confirmed as the genuine,
    currently-shipping kernel package (not a stale leftover).

  - update_control(): same pattern for control-*.tar.xz into
    /usr/prog/PROGRAM/control/<version>/, but does NOT run run.sh
    immediately (that call is commented out) - confirms the two-phase
    design: this step only STAGES the control firmware. The real
    Update/UpdateM trigger flag files ship AS PART OF the
    control-1.1.1.tar.xz payload itself (confirmed - both are present,
    real, empty 0-byte files inside the extracted package) - so once
    staged, they're already in place for app_startup.sh's
    CONTRIL_FLAG/CONTRIL_M check to find and run ./run.sh on the NEXT
    boot. No separate "set the flag" step exists - shipping the flag
    files IS the mechanism.

  - update_software(): same pattern for software-*.tar.xz into

  - update_library(): same pattern for library-*.tar.xz.

  - update_other(): a real grab-bag bucket, not versioned/staged like
