[~] UPDATE 2 (latest): the same dump_mcu.py read was run on the
    MAINBOARD (/dev/ttyS2) and matches NationsCommand's UCID/UID
    byte-for-byte - the Nations layout (UCID @0x1FFFF7C0, UID
    @0x1FFFF7F0) is now confirmed against a known-Nations chip, and the

    UPDATE 4 - RESOLVED via web search: the OpenOCD N32G45x driver patch
    documents the DBG_ID layout. Decoded: BOTH boards are N32G455
    (dev_id 0x455). Mainboard = 512 KiB flash / 144 KiB SRAM (read
    live); eboard = 256 KiB flash / 144 KiB SRAM (inferred from its

    against the Nations user manual itself (section 29.4.2; device model
    0x455 = N32G455) - see software/boards/boot-entry-and-gpio.txt. The
    eboard's flash size was later read live too (0x8F544511, 256 KiB).
    The g992/flashforge-ad5m-5mpro-research repo

    images (J-Link, 0x08000000), no reply reports a working one, and

    RAM, 128 MHz) were called the smallest variant. That repo covers the

[x] EBOARD BOOTLOADER FULLY DISASSEMBLED (software/boards/eboard/
    bootloader.txt): XMODEM-CRC-like protocol; idles printing "Ready." after
    a cold boot until it gets 0x41 ('A'); an app-initiated reset sets magic
    0x1234 in backup register 4 so it chains back to the app; a bare 'C'
    (0x43) makes it erase 160 KiB of app flash. Host half of the handshake
    exists as the stock /usr/prog/klipper/checkEboard tool. Consistent with
    IAPCommand's sync/write code and xblax's boot_eboard_mcu. Sharpens
    (does not confirm) the eboard-outage hypothesis.
[x] What sends the eboard start byte at boot - FOUND: the stock GUI itself.
    firmwareExe's main() calls bootSerialMainEboardMcu() (same routine as the
    standalone checkEboard: waits for "Ready" on /dev/ttyS5 at 115200, sends
    0x41). Klipper restarts never involve it, which fits the eboard-outage
    hypothesis (reset without the magic strands the board at "Ready.").
    Bootloader serial settings decoded too: 115200 8N1 (IAPCommand uses even
    parity). See software/boards/eboard/bootloader.txt. Still untested:
    the outage hypothesis itself.

[~] How the host puts an MCU into the ROM BOOT - ANSWERED for the
    mainboard by offline disassembly + the Nations user manual (now
    obtained): NationsCommand raises host GPIO 50 (BOOT0 by my reading),
    pulses GPIO 49 low ~200 ms (NRST), so the chip re-latches BOOT0 and
    starts the ROM bootloader; bare `-c` never resets it back out, which
    explains the mainboard outage. What is still not proven: that 49/50
    really are NRST/BOOT0 (schematic needed) and nothing was observed
    live. See software/boards/boot-entry-and-gpio.txt.
